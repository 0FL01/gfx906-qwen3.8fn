# Задача: специализированный inference core для gfx906

## Миссия

Построить работающий и измеримо быстрый inference core на C++20 + HIP для Qwen3.8-Flash-Next на выделенной машине: две gfx906 по 16 GiB, Xeon E5-2698B v3, 128 GB заявленной quad-channel DDR3-1600. CPU-путь: AVX2/FMA/F16C после проверки возможностей. GPU-путь: wave64, HIP streams, AMDGCN intrinsics и точечный inline assembly. Одна интерактивная сессия, layer split, эксперты в RAM с GPU-кешем, затем MTP2.

Код редактируется в текущем Git-репозитории на машине агента. Сборка, GPU-запуски и окончательные CPU-замеры выполняются на целевой машине через SSH. Код контроллера не определяет ISA целевого CPU.

Это реализация, не подготовка ещё одного проекта реализации. После первичного RECON переходить к вертикальному работающему срезу. Новая документация допускается, когда она помогает текущему коду, измерению или продолжению сессии.

## Первое чтение

Прочитать START.md, затем STATE.md, RECON.md и PLAN.md. После возобновления контекста обычно достаточно STATE.md, текущей задачи PLAN.md и соответствующего раздела RECON.md. Не перечитывать весь интернет и не повторять аппаратный RECON без изменения машины/стека.

Начальный пакет не содержит результатов SSH-проверки и не содержит готового движка. Все целевые скорости являются целями, а не доказанными свойствами реализации.

## Режим работы

Работать автономно: выбрать ближайшую задачу, изменить код, переслать изменения, собрать, запустить небольшой релевантный тест, измерить, оставить полезное изменение, продолжить. Не останавливаться после выдачи плана или одного успешного kernel smoke.

Машина целиком выделена пользователем под разработку. Можно останавливать старый llama-server, устанавливать необходимые зависимости, менять конфигурацию запуска, чистить свои build/run-файлы и перезапускать свои процессы. Не запрашивать подтверждение каждого такого действия. Не ломать SSH и маршрутизацию: это транспорт самой разработки. Рискованные изменения ОС/драйвера делать только для наблюдаемой проблемы, а не ради новизны версии. Не публиковать ключи, пароли и API-токены в Git или логах.

Обычный цикл:

1. Сформулировать одну проверяемую гипотезу о текущем узком месте.
2. Внести минимальное изменение. Если требуется большая переделка, сначала получить исполнимый срез.
3. Собрать на GPU-машине. Проверять exit status, в том числе за `tee`.
4. Выполнить тест затронутой семантики и короткий замер.
5. Для кандидата на основной путь сделать парное A/B или A/B/A. Не принимать единичный всплеск за ускорение.
6. Сделать обычный Git commit и записать результат в STATE.md. Неуспешные идеи отмечать кратко, чтобы не повторять их.

## KISS / YAGNI / Pareto

Не строить универсальный tensor framework, graph IR, backend registry, JIT/autotuning-платформу, distributed scheduler, plugin system или универсальный сервер моделей. Не проектировать переносимость на NVIDIA/RDNA/CDNA. Не добавлять training, vision, LoRA, tensor parallelism, continuous batching, paged KV, KV-offload и speculative trees до выполнения основных целей.

Не писать самостоятельно tokenizer, JSON parser, HTTP stack, GEMM-библиотеку и всё ggml. Допускаются существующий tokenizer, JSON-библиотека, rocBLAS и небольшие переиспользуемые компоненты. Сохранять необходимые лицензии и attribution. Существующие реализации служат донорами решений и проверками, но конечный hot path исполняется собственным runtime, не вызовом llama_decode под другим именем.

Не создавать запасные копии моделей, архивы рабочей директории, матрёшку worktree или собственную систему управления экспериментами. Не считать sha256sum моделей. Для происхождения замера достаточно обычного Git commit, флага dirty при необходимости, имени варианта модели, параметров и сырого лога. Одна основная ветка, один текущий baseline, один кандидат.

Не ограничивать число итераций искусственным сроком. Не расширять scope, чтобы избегать сложного участка. Если несколько корректных кандидатов не дают выигрыша, зафиксировать отрицательный результат и перейти к следующему измеренному узкому месту.

## Что нельзя упростить

Нельзя выкидывать экспертов, уменьшать top-k/budget QSA, менять веса, precision, PLE, tokenizer или sampling и называть результат ускорением того же движка без явного указания изменения.

Нельзя подменять проверки logits проверкой «ответ выглядит нормальным». Нельзя ослаблять tolerances исключительно ради прохождения своего kernel. Различия в порядке FP-суммирования допустимы при измеренной ограниченной ошибке; битовая идентичность всей генерации между разными вычислительными путями не является универсальным требованием.

Критичные инварианты: правильные token IDs; hash/offset PLE; QSA causal visibility, фактический хвост и выбранные IDs; суммы экспертных вкладов; корректное состояние после отклонения MTP; отсутствие NaN, OOB и чтения ещё не загруженного cache slot.

Проверка dimensions/offsets/размеров в loader обязательна. Это защита от неверного чтения памяти, а не церемония с контрольными суммами.

## Источники истины

Фактическая геометрия и dtypes берутся из загружаемых тензоров/metadata. Исходный config и Transformers определяют архитектуру. Текущий fork определяет эксплуатационный baseline на имеющемся GGUF, но не считается безошибочной математической спецификацией. Strata является донором идей, не автоматическим oracle.

Особое внимание: у HF QSA выбираются полные блоки и фактический хвост. В указанном production fork виден top-k по развёрнутым позициям с вместимостью до 2051. Сначала проверить семантику на границах; не объявлять эти пути эквивалентными по комментарию. Для математически правильного core приоритет у подтверждённой reference-семантики. Обнаруженное исправление baseline маркировать отдельно от чистой оптимизации. Не поддерживать две постоянные реализации ради исторического бага, если достаточно диагностического сравнения.

## Стартовая модель и следующие варианты

Сначала исполнять имеющийся `qwen38-keep1-Q4_0.gguf` без реквантизации и существующий MTP sidecar после завершения non-speculative пути. Упаковку разрешено менять без изменения значений весов.

Потом сделать потоковый converter из оригинальных safetensors в один простой runtime-pack. Полную PLE и собственную квантизацию оценивать отдельно. Названия вариантов явно различают keep1/full-PLE и precision. Сохранять базовый GGUF и рабочий существующий образ как уже имеющийся эталон; не дублировать их.

## Аппаратная дисциплина

Не принимать название карты из fastfetch за объём памяти. Проверить HIP device properties и реальную VRAM. Не принимать число потоков CPU за число физических ядер. Не придумывать NUMA-узлы: обнаружить topology, на одном узле использовать простой affinity/first-touch.

Использовать уже работающий gfx906 toolchain, если он доступен. Отдельно проверить HIP kernel и rocBLAS GEMM: компилятор, runtime и набор rocBLAS kernels могут иметь разную совместимость. Не подменять gfx906 на gfx908/gfx90a для обхода отсутствующего kernel.

Одна измерительная GPU-нагрузка одновременно. Не компилировать тяжёлые файлы и не конвертировать модель во время финального performance-прогона. Не держать baseline и кандидат загруженными одновременно, если они конкурируют за RAM/VRAM.

## Измерения

Три уровня: маленький correctness fixture; локальный kernel/block benchmark; полный запрос. Полный набор длинных запросов нужен для вехи или изменения длинного контекста, а не после каждого исправления синтаксиса.

Разделять: PP без prefix reuse; incremental PP на новой части; TG с реально занятой историей; полный запрос; холодный/прогретый expert cache. Считать фактически сгенерированные токены и прошедшее время. Draft-кандидаты не являются выходными токенами. В MTP регистрировать число окон с 0/1/2 принятыми draft-токенами и стоимость draft/verify/restore.

Трассировка и GPU events включаются отдельно. Не складывать перекрывающиеся интервалы в «общую latency» и не выдавать host enqueue-time за завершённый GPU runtime. После диагностики подтверждать ускорение без подробного tracing.

Промежуточный smoke: короткий вход, 32-128 выходных токенов. Подтверждение скорости: 512 выходных токенов, несколько фиксированных входов, несколько повторов. Для основной серии сохранить исходный sampling пользователя: temperature 1.0, top-p 0.95, top-k 20. Greedy использовать отдельно для диагностики.

## Память между сессиями агента

STATE.md должен оставаться коротким: рабочая команда сборки/запуска, текущая задача, последнее подтверждённое измерение, найденная проблема, следующие конкретные действия. Подробные численные результаты хранить в одном results.jsonl и сырых run logs, а не пересказывать в десятках документов.

Доступ к `mi50-llama-remote` может быть нестабильным: сервер подключён через LTE и реверс-туннель; возможны всплески трафика, задержки и обрывы сети. При сетевом отвале не завершать разработку из-за временной недоступности: ждать через `sleep` с экспоненциальным backoff между проверками связи (1, 2, 4, 8, затем 10 минут); при дальнейшем отсутствии связи проверять раз в 10 минут, после восстановления сбросить backoff. Не менять SSH, туннель или маршрутизацию ради обхода временного сбоя.

После падения или обрыва SSH сначала проверить существующий процесс и последний лог, когда связь восстановится. Не считать обрыв соединения остановкой удалённой задачи и не запускать второй экземпляр той же тяжёлой задачи вслепую.

## Завершение вехи

Веха закрывается работающим кодом, командой воспроизведения, результатом теста и честным замером. Если скорость не достигнута, указать фактическое узкое место и продолжать по PLAN.md. Не объявлять весь проект успешным по скорости одного GEMV или по скомпилированному executable.
